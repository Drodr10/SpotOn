Getting the backend off ngrok

Right now the Flask backend only exists on whoever's laptop is running it, behind an ngrok URL that changes. That can't ship to the App Store. Here's the plan, what it costs, and who needs to do what.

Why we can't ship as-is

The backend has to be reachable at a fixed public HTTPS address for four separate reasons. An ngrok URL rotates, so it fails the first three:

  • Stripe sends webhooks to it. That's the reliable backstop that creates a reservation after payment — if it can't reach us, bookings depend entirely on the app's own follow-up call.
  • Stripe seller onboarding redirects back to it in a real browser.
  • The app on people's phones calls it for pricing, booking, and payouts.
  • The background sweeps need something to trigger them on a schedule.

Expo isn't involved in any of this — it only serves JavaScript to a development build. It was never going to host the backend.

Why not the free instance

It spins down after 15 minutes of no traffic and takes about a minute to wake. Someone tapping Book after a quiet spell would sit on a spinner. It also gets 0.1 CPU against Starter's 0.5. Not worth $7 to find out.

What each of us has to do

Almost nothing, for most of us

Render deploys automatically from GitHub. Push to main, it builds and ships. You don't need a Render login to write code or release it.

A login is only needed to change environment variables, read logs, restart the service, or manage the cron jobs — an ops job, not a per-person one. The Hobby plan includes one seat, and since we share a team email, that covers it. If we ever need two people in the dashboard at once, Pro is $25/mo for unlimited seats and we can decide then.

The setup

Done once, by whoever has the shared login. Roughly half an hour.

  1. Create a Web Service — not a Private Service

    Connect the GitHub repo and pick Web Service. Render's naming is misleading: “web” means gets a public URL, not serves a website. Our JSON API qualifies. A Private Service is reachable only from inside Render's own network, so Stripe and everyone's phones would be locked out.

  2. Point it at the backend folder

    Root Directorybackend
    Build Commandpip install -r requirements.txt
    Start Commandgunicorn app:app --workers 2 --timeout 60
    Health Check Path/api/health
    Instance TypeStarter$7/mo

    Gunicorn is already in requirements.txt and the Python version is pinned in .python-version, so there's nothing to install or configure beyond this.

  3. Set the environment variables

    Copy these from backend/.env, with one addition and one change:

    SUPABASE_URL=
SUPABASE_KEY=              # service-role key — never commit this
STRIPE_PUBLISHABLE_KEY=
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=     # NEW value, from step 5
BACKEND_URL=https://<our-render-domain>
SWEEP_SECRET=
ENABLE_SWEEP_SCHEDULER=false   # ← see warning below

  4. Add two cron jobs

    These replace the scheduler that currently runs inside the app process. Every 10 minutes each:

    curl -fsS -X POST https://<domain>/api/stripe/run-payout-sweep \
  -H "X-Sweep-Secret: $SWEEP_SECRET"

curl -fsS -X POST https://<domain>/api/stripe/run-notification-sweep \
  -H "X-Sweep-Secret: $SWEEP_SECRET"

    Both return 401 without the header, so a wrong secret fails loudly rather than silently doing nothing.

  5. Register the Stripe webhook

    In the Stripe dashboard, add an endpoint pointing at:

    https://<domain>/api/stripe/webhook

    Then copy that endpoint's signing secret into STRIPE_WEBHOOK_SECRET. It's generated per endpoint — it is not the same value we use locally with stripe listen.

  6. Point the app at the new address

    Set EXPO_PUBLIC_IP to the bare hostname — no https://, no /api:

    EXPO_PUBLIC_IP=spoton-api.onrender.com

    That's the only change the app needs; every call site already builds the rest of the URL. Set it as an EAS environment variable, along with the Supabase keys and the Maps key — EAS does not upload .env files, so anything only in .env ships as undefined.

  7. Check it's actually up

    curl https://<domain>/api/health
# {"status":"ok"}

    Then make one real booking end to end and confirm the reservation appears. That exercises the app call, the webhook, and the database in one go.

Three things that fail silently

Each of these deploys cleanly, looks fine, and is wrong. They're worth knowing about in advance because none of them announce themselves.

1 Forgetting ENABLE_SWEEP_SCHEDULER=false costs real money

The app defaults this to on, and its other safety check doesn't apply under gunicorn. With two workers, that means two schedulers running the payout sweep at the same time, against real Stripe transfers. This must be set on the very first deploy, not added later.

2 The webhook path needs the /api prefix

It is /api/stripe/webhook — the /api is the easy bit to drop. Get it wrong and Stripe records delivery attempts, the app looks healthy, and we quietly lose the backstop that creates reservations when the app's own call doesn't land. Same prefix on both cron URLs.

3 Private Service instead of Web Service

Same price, same hardware, no public address. It deploys successfully and then nothing on the internet can reach it.

Going live on Stripe — later, but plan for it

Everything above works in Stripe's test mode. Switching to live mode is a separate step, and it's more than swapping keys:

  • New API keys — pk_live_ / sk_live_ instead of the test pair.
  • A new webhook secret. Endpoints are configured per mode, so we create ours again in live mode and it gets a different signing secret.
  • Every seller re-onboards. Connect accounts don't carry across modes, and our database currently stores test-mode account IDs — those rows have to be cleared at cutover or sellers get handed a dead account.

! Start Stripe account activation now

Live mode requires our own Stripe account to be fully activated — business details, bank account, tax info, and a review by Stripe that can take days. It's the one step with real lead time and the only one that can't be done on launch day.

Still open

  • Bandwidth. Hobby includes 5 GB/month outbound. Listing images come from Supabase rather than through Flask, so this is JSON only and should be fine — but it's the first limit likely to bind.
  • Two ungated endpoints. /api/stripe/finalize-booking and /api/stripe/release-hold still have no authentication. Worth closing before we're taking real money.
