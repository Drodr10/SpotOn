## 2. Blocker — notifications cannot work in prod, and fail silently

**The `notification_events` table does not exist on the hosted database.**

The migration that creates it (`20260720120000_add_notification_events.sql`) is committed to
`main`, but merging a migration file does not apply it to the hosted DB. It was never applied.

Why this makes the Jul-29 "test to see if these work" task fail 100%:

`backend/services/notifications.py` — `_send_once()` writes the dedupe row **before** sending:

```python
if not _insert_event(str(res["id"]), event_key, str(profile["id"]), title, body, payload, status):
    return False
send_push(token, title, body, payload)
```

`_insert_event` catches every exception and returns `False` (`notifications.py:93-97`). With the
table missing, the insert always throws, `_send_once` always returns early, and **`send_push` is
never reached**. No error surfaces to the app — only a `print` in the backend log. Every
notification test reads as "notifications are broken" with nothing in the UI to explain it.

**Fix before QA touches notifications:** apply `20260720120000_add_notification_events.sql`.

### This is the only thing blocking notifications — other preconditions check out

- `profiles.expo_push_token` — **live** (so `_profile()` resolves and tokens can be read).
- `profiles.payouts_enabled`, `profiles.stripe_account_id` — **live**.
- The sweep that fires start/end notifications is on by default: `app.py:49` gates
  `_start_sweep_scheduler()` on `ENABLE_SWEEP_SCHEDULER` defaulting to `"true"`, and
  `backend/.env` sets it `true` with `SWEEP_INTERVAL_SECONDS=60`. Confirm the same on the
  deployed backend — booking notifications go through the Stripe webhook, start/end go through
  this sweep, and they can fail independently.

### How the absence was established

Read-only PostgREST probes with an anon-role key. Two independent lines of evidence:

1. **RLS-shape control.** `notification_events` has RLS enabled with no policies or grants, so
   "not visible" and "not present" are normally indistinguishable — except `reservation_holds`
   (`20260710120000`) has the **identical** RLS-on/no-policy/no-grant shape and probed PRESENT
   under the same key. Same visibility conditions, different result.
2. **Monotone application order.** `0705`, `0710`, `0712120000`, `0712140000` all probed present;
   `0720` is the first and only gap. That is the signature of migrations hand-applied in order,
   stopping one short of the last. (`0711` sits inside that run but creates only a function, so it
   could not be probed — it is assumed applied on the strength of this ordering, not observed.)

## 5. #21 — correction: this has no migration dependency

I initially grouped #21 under "blocked on `20260730005125`". **That was wrong.** That migration
governs `reservation_validation_error()` — *reservation* rate validation. #21 is about *listing
creation* form state, which is pure frontend and already in `main`.

`CreateListing2.tsx:112-124` builds the payload as a clean either/or, explicitly nulling the
other mode's tiers rather than carrying them over:

```js
// hourly mode                        // weekly mode
hourly_rate: state.pricePerHour,      hourly_rate: null,
daily_rate:  accepted ? perDay : null, daily_rate:  null,
weekly_rate: null,                    weekly_rate: state.pricePerWeek,
monthly_rate: null,                   monthly_rate: accepted ? perMonth : null,
```

Stale rates from the abandoned mode are written as `null`, and the optional tiers are gated on
their `*Accepted` flags. **Testable now; expected to pass.**

## 6. #46 — the list's description is wrong; the underlying bug is real

The list says "you can select any number of weeks, no limit." There **is** a cap:
`HARD_CAP_WEEKS = 52` (`search.tsx:1251`, on every branch including `main`). At 52 it merely feels
unbounded while scrolling.

The real defect is different and worse:

```js
const weeklyEnd = useMemo(
  () => new Date(weeklyStart.getTime() + currentWeeks * 7 * 24 * 3_600_000),
  [weeklyStart, currentWeeks],
);                                         // search.tsx:1540-1543
```

`weeklyEnd` is derived purely from the week count and never consults `listing.available_until`.
`available_until` appears in exactly one place in the whole booking flow — `maxDate` on the
**hourly** Schedule picker (`search.tsx:2243`). So the hourly path is bounded (#38 is 🟢) and the
weekly path is not: you can book 52 weeks on a listing that stops being available next month.

**Already assigned.** Same defect as the Jul-29 item *"For monthly/weekly reservations, they should
not be able to be reserved after the listing date ends… No safeguards for this currently"* →
**@Ehan**. Flagging so it is not done twice. Re-word #46 to "weekly/monthly end is not clamped to
`available_until`" rather than "no cap."

## 7. #67 / #68 — server-side window enforcement is genuinely missing

Worth being precise, because the UI may make these *look* like they pass.

The live `20260712120000` uses `available_from` / `available_until` **only** inside
`get_visible_listings()` — i.e. for search visibility. It adds no check on reservation creation.
The unmerged `20260808140000` says so in its own header:

> *"available_from / available_until were read in exactly one place … Because nothing raised, the
> auto-refund path …"*

It is that migration which adds the rules to `reservation_validation_error()` — rejecting
`p_start_time < available_from` (:95-98) and `p_end_time > available_until` (:101-104).

So today: the hourly picker's `maxDate` blocks the obvious UI route, but nothing server-side
rejects an out-of-window reservation. A tester clicking through the happy path may mark #67/#68
green while the hole is still open — and the weekly path (§6) has no `maxDate` at all, so it
reaches the server unguarded. **Park these until PR #70 is merged *and* its migration applied.**

## 9. #91 — seller with existing Stripe account (marked IMPORTANT)

**The in-app duplicate path is guarded.** `createConnectAccount()`
(`backend/services/stripe_client.py:331-357`) reads `profiles.stripe_account_id` first and returns
it without creating when set (:340-341), then persists the new id immediately after create (:354)
so a dropped client cannot orphan an account.

Also worth clearing: `ce5ebe9 "Removed check for Stripe ID when trying to create listing"` came in
with holdPayouts, but it removed a **listing-creation** precondition, not this dedupe. It does not
affect #91.

**The gap that remains,** and what #91 should actually test: a seller with a Stripe account that
`profiles.stripe_account_id` does not know about — created before this code landed, or where the
:354 update failed after `Account.create` succeeded. Stripe permits multiple Express accounts per
email, so that seller gets a second account and payouts land on the wrong one. Test by clearing
`stripe_account_id` on a profile that already has a live Stripe account, then running onboarding.
